# 体验反馈工作台

一个帮助非产品岗位新人把零散产品体验整理成结构化反馈的轻量网页工具。

## 项目背景

项目来自一次真实但已匿名化的个人工作观察：一名市场实习生在体验某 AI 产品、整理问题并向产品同学反馈时，最初依靠文档、截图和零散文字记录。由于缺少结构化反馈方法，信息容易不完整、事实与判断混在一起，表达也较混乱，沟通中需要多轮补充。

由此产生的产品假设是：部分缺少产品表达经验的非产品岗位新人，可能也需要一套简单的反馈整理方法。**这只是基于个人工作观察提出的假设，不是已经得到普遍用户验证的结论。**

## 目标用户

- 市场实习生。
- 内容、用户、增长运营新人。
- 需要向产品或研发同学反馈问题，但缺少产品表达经验的非产品岗位人员。

## 已实现的核心用户流程

首页查看历史反馈 → 新建反馈 → 三步填写 → 完整度检查 → 结构化预览 → 复制纯文本 → 保存到浏览器本地 → 编辑和删除历史反馈。

## 已实现的功能

- 三步引导式反馈表单，依次整理“使用场景—问题事实—影响与期望”。
- 操作步骤逐条添加和删除。
- 将实际结果、预期结果和影响分开填写。
- 三种完整度状态：缺少关键信息、建议补充、基本完整。
- 用温和建议提醒用户补充信息，不判断内容是否正确。
- 结构化反馈预览与结构化纯文本复制。
- 在浏览器本地保存历史反馈，并按更新时间从新到旧展示。
- 编辑已有反馈时更新原记录，不创建重复副本。
- 删除历史反馈前二次确认。
- 删除记录时清除对应临时草稿，避免已打开的旧预览页重新恢复已删除记录。
- 在页面中展示匿名、隐私和本地保存提醒。

## 技术实现

项目只使用浏览器本身支持的基础技术：

- **原生 HTML**：负责页面内容和结构。
- **原生 CSS**：负责页面样式。
- **原生 JavaScript**：负责三步切换、检查、复制、保存、编辑和删除等交互。
- **`sessionStorage`**：保存当前标签页的临时草稿；它可以理解为只服务于本次填写的临时存放区。
- **`localStorage`**：保存当前浏览器中的历史反馈；它可以理解为网站在本机浏览器里的小型存放区。

项目不使用前端框架，不使用云端数据库，也不接入 AI 接口。因此无需安装项目依赖，也没有账号、在线同步或 AI 润色能力。

## 本地运行

1. 在终端进入包含 `index.html` 的项目目录。
2. 启动本地服务器：

   ```bash
   python -m http.server 8000 --bind 127.0.0.1
   ```

3. 在浏览器打开：<http://127.0.0.1:8000/>

历史反馈保存在当前浏览器与当前访问地址对应的本地空间。更换浏览器、更换访问地址或清除浏览器数据后，可能看不到之前保存的记录。

## 测试说明

现有自动化测试使用 Node.js 自带的断言能力，可分别运行：

```bash
node tests/feedback-text.test.js
node tests/history-storage.test.js
node tests/preview-save-draft.test.js
```

- `tests/feedback-text.test.js`：检查结构化纯文本的字段、步骤、选填内容和异常输入处理。
- `tests/history-storage.test.js`：检查历史记录的保存、更新、排序基础数据、删除、异常数据过滤和写入失败处理。
- `tests/preview-save-draft.test.js`：检查预览页保存时是否使用最新草稿，以及草稿失效、记录已删除或记录不匹配时不会错误保存。

项目主要流程已经进行手动功能验收。这里不把手动验收等同于用户研究，也不编造测试人数、使用次数、效率提升比例或用户反馈。

## 当前限制与后续方向

- 尚未开展正式用户访谈，问题是否普遍存在仍待验证。
- 尚未开展正式可用性测试，三步表单能否降低整理难度仍待验证。
- 当前只支持单人、当前本地浏览器使用，没有账号、云端同步或多人协作。
- 工具只帮助整理表达，不保证产品团队一定理解或采纳反馈。
- 工具不自动判断需求是否合理，也不判断需求优先级。

后续若进入验证阶段，应先用匿名案例访谈和观察相似岗位用户，再根据真实结果决定是否调整字段与提示，而不是直接扩大功能范围。

## 隐私提醒

请勿填写真实公司、产品、部门、同事、客户或内部资料名称，演示时统一使用“市场实习生”“某 AI 产品”“产品同学”等匿名表达。历史数据只保存在当前浏览器，清除浏览器数据后可能丢失，也不会自动同步到其他浏览器或设备。
